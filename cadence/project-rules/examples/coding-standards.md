# 项目代码开发规范示例

> **说明**：这是一个适用于 AI 编码助手的项目级代码开发规范示例。
>
> **目标**：不是提供通用语言风格清单，而是帮助 AI 在具体仓库中生成“贴近现有项目、最小风险、便于团队接手”的代码。
>
> **使用方法**：
> 1. 复制此文件到 `cadence/project-rules/` 目录
> 2. 结合项目技术栈、目录结构、历史代码风格进行定制
> 3. 在 `CLAUDE.md` 或 `AGENTS.md` 中引用该文件

## 1. 总体原则

### 1.1 先遵循仓库事实，再遵循通用最佳实践

本项目可能已经演进多年，存在历史代码风格差异。AI 编码时按以下优先级执行：

1. 优先遵循当前模块、当前目录、当前功能附近的既有实现方式。
2. 若局部风格不一致，优先复用同类文件中的主流写法。
3. 仅在新增代码或明确重构任务中引入更规范的写法。
4. 不因一次需求顺手统一全仓历史风格。

### 1.2 默认策略是最小改动

- 优先修改已有类、函数、模块，而不是新建抽象层。
- 非必要不重命名类、方法、接口、路由、SQL id、配置项。
- 非任务要求不移动目录结构、不替换框架、不大面积格式化。
- 改动应沿着真实调用链展开，避免只改一层导致上下游不兼容。

### 1.3 AI 输出必须便于人工维护

- 优先写清晰代码，不炫技。
- 命名贴近业务语义，避免无语义缩写。
- 复杂逻辑使用少量注释解释“为什么这样做”。
- 不引入项目未使用的新框架、新范式、新依赖，除非需求明确要求。

## 2. 先写项目事实

> 本节必须由项目初始化时结合代码库实际情况填写，不能保留空泛描述。

### 2.1 模块与目录职责

| 模块/目录 | 职责 | 备注 |
|-----------|------|------|
| `index.html` | 页面骨架、HUD、虚拟按键区、内联 CSS 主题变量 | 唯一 DOM 入口 |
| `game.js` | 全部游戏逻辑（引擎层 / 输入层 / 游戏层 / 渲染层） | 单文件 IIFE，不做模块拆分 |
| `openspec/` | OpenSpec 配置与后续 change 产物 | `config.yaml` 由规则受管 |
| `cadence/` | Cadence 产物目录（designs / plans / project-rules 等） | 不参与运行时 |

DOM id 契约：`stage`、`game`、`hud`、`fps`、`hint`、`pad`。

### 2.2 主要技术栈

- 语言/版本: JavaScript（浏览器原生，`'use strict'` + IIFE 封装，无转译）
- Web 框架: 无框架；Canvas 2D API + `requestAnimationFrame`
- ORM/数据访问: 无（纯客户端，无持久化）
- RPC/MQ/任务调度: 无
- 测试框架: 无（`npm test` 为占位脚本 `no test specified`）；建议 Node 内置 `node:test` 覆盖 `game.js` 中的纯函数

### 2.3 项目现有主流模式

- 输入如何接收: 键盘 `keydown/keyup` 经 `KEY_MAP` 映射到 `keys`，触屏 `#pad button` 的 `pointerdown/up/cancel/leave` 写同一份 `keys`；跳跃用边沿位 `jumpQueued`
- 输出结构是什么: 无 API；对外契约为纯函数签名与 `player = { x, y, w, h, vx, vy, onGround }`
- 异常处理方式是什么: 无异常体系；用状态字段 + 早返回表达
- 日志方式是什么: 无日志框架；仓库当前不使用 `console`
- 数据访问层命名是什么: 无数据访问层

## 3. AI 修改代码时的执行规则

### 3.1 新增功能时

- 先判断功能应该落在哪一层，不要默认写进 controller 或 service。
- 先搜索同类实现作为模板，再开始新增代码。
- 新接口、新 DTO/BO、数据访问方法、配置项命名要与周边保持一致。

### 3.2 修改功能时

- 先沿调用链确认影响范围：入口、服务、数据访问、配置、测试是否联动。
- 默认最小改动，不顺手修 unrelated 问题。
- 只修与本次需求直接相关的历史问题。

### 3.3 重构时

- 必须保持对外接口、函数签名、配置名称、数据库契约的兼容性，除非需求明确允许变更。
- 重构目标应聚焦：提炼重复逻辑、拆长函数、补校验、补日志、补测试。
- 不做全仓风格统一式重构。

## 4. 分层与边界规则

> 按项目实际分层填写。本节要写“允许做什么”和“禁止做什么”，不要只写层级图。

### 4.1 推荐调用链

`输入层(keys / jumpQueued) -> 主循环(frame，固定步长) -> 游戏层(update) -> 物理纯函数(stepPhysics / resolveCollisions) -> 渲染层(render / draw*)`

### 4.2 各层职责

#### 输入层

- 负责 `[键盘与触屏事件 -> 统一按键状态 keys + 边沿位 jumpQueued]`
- 不直接操作 `[物理计算与绘制]`

#### 游戏层与物理纯函数

- 负责 `[状态更新、跳跃请求消费、敌人/道具/关卡推进]`
- 物理与碰撞解算必须保持为纯函数（入参出参都是纯数据、不触碰 DOM），便于补测试
- 不负责 `[直接绘制像素、查询 DOM]`

#### 渲染层

- 负责 `[按逻辑坐标 960×540 绘制背景与实体]`
- 不负责 `[修改物理状态；渲染不得产生副作用]`

### 4.3 严禁事项

- 物理/碰撞逻辑里访问 DOM 或读取 `window`
- 在渲染函数里修改 `player` 状态
- 为了复用引入与当前单文件结构不一致的新架构层
- 未经评估引入新的统一包装结构或第三方框架
- 新增与 `player` 并行的第二份状态对象

## 5. 命名规范

### 5.1 基础命名

| 类型 | 规则 | 示例 |
|------|------|------|
| 类/组件/模块 | PascalCase 或按项目约定 | `UserController` |
| 方法/函数 | camelCase 或按语言约定 | `getUserById` |
| 变量 | camelCase 或按语言约定 | `userName` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| 包/目录 | 小写或按项目约定 | `com.example.order` |

### 5.2 项目专属命名

- 控制器/入口层后缀: `[例如 Controller / Handler / Route]`
- 服务实现后缀: `[例如 ServiceImpl / UseCase / Processor]`
- 数据访问后缀: `[例如 DAO / Mapper / Repository]`
- 数据对象后缀: `[例如 PO / Entity / Record / DO]`
- 传输对象后缀: `[例如 DTO / BO / VO / Req / Resp]`

### 5.3 命名原则

- 优先复用项目现有命名体系，不强行引入另一套风格。
- 若仓库同时存在多套命名，新增代码优先贴近同目录主流模式。
- 不要为了“更规范”重命名一整条调用链。

## 6. 接口与返回值规范

> 本节必须填写项目真实返回结构，不能套通用模板。

### 6.1 对外契约结构

本项目无 HTTP 接口，对外契约是纯函数签名与状态结构：

```js
stepPhysics(state, input, dt, env)   // 入参出参均为纯数据，就地更新并返回 state
resolveCollisions(state, env)        // 边界与地面碰撞解算，就地更新并返回 state
```

`player` 状态结构：`{ x, y, w, h, vx, vy, onGround }`。

### 6.2 规则

- 新增函数沿用现有纯函数签名风格：入参出参都是纯数据、不触碰 DOM。
- 不新增与 `player` 并行的状态对象，也不引入响应体包装。
- 参数语义或顺序变更必须同步更新调用方（`update(dt)`）与本规范。
- 新增可调参数优先放进 `PHYSICS_ENV`，不要散落魔法数字。

### 6.3 入参处理

- 输入统一走 `keys` + `jumpQueued`，不要在业务逻辑里再读键盘事件。
- 参数无效时按现有钳制/早返回方式处理（`clamp` 已有先例），不要静默吞掉。

## 7. 异常处理规范

### 7.1 使用项目现有异常体系

- 业务校验失败: `[无异常体系；用状态字段与早返回表达，例如 onGround=false 表示未落地]`
- 系统异常: `[浏览器端不使用异常体系承载游戏逻辑；确需兜底时用 try/catch 并给出可定位信息]`
- 外部依赖失败: `[当前无外部依赖；未来引入网络请求时明确失败态与重试策略]`

### 7.2 规则

- 不要捕获异常后什么都不做。
- 不要只打印异常，不返回上下文。
- 返回失败对象时，必须设置完整失败信息。
- 抛异常时，异常描述中必须带业务上下文。

### 7.3 异常信息要求

- 使用团队习惯语言。
- 带关键业务标识，如订单号、用户 ID、店铺 ID、任务 ID、外部流水号等。
- 避免只写“系统异常”“处理失败”这类无定位价值的信息。

## 8. 日志规范

### 8.1 日志框架

- 使用 `[仓库当前无日志框架；调试期临时 console.debug 必须在提交前移除]`
- 禁止把调试输出长期留在代码里；禁止引入与项目体量不匹配的日志框架

### 8.2 日志级别

| 级别 | 使用场景 |
|------|----------|
| `DEBUG` | 调试细节、详细出入参 |
| `INFO` | 核心流程节点、关键状态变化 |
| `WARN` | 异常但流程可继续 |
| `ERROR` | 流程失败、关键依赖异常 |

### 8.3 日志内容要求

- 至少包含一个关键业务标识。
- 记录“动作 + 对象 + 结果”。
- 异常日志必须带堆栈。
- 大对象日志需谨慎，避免无节制打印完整报文。

## 9. 注释规范

### 9.1 原则

- 注释解释“业务原因、边界条件、历史兼容”，不要重复代码表面含义。
- 复杂分支、状态流转、平台差异、临时兼容逻辑需要注释。
- 优先少而精的注释。

### 9.2 不建议的注释

- “给变量赋值”
- “调用某方法”
- 与代码逐行重复的说明

## 10. 数据访问与 SQL 规范

> 本项目当前无任何数据访问与 SQL（纯客户端、无持久化）。本节仅在引入持久化（如 `localStorage` 存最高分）时启用；启用时需同步更新本节与 `design-template.md` §1.3。

### 10.1 通用要求

- 避免 `SELECT *`
- 接口方法名、SQL id、映射配置要一一对应
- 参数类型、返回类型与代码保持一致

### 10.2 动态 SQL / 查询构造规则

- 优先使用项目既有的安全写法
- 动态排序、动态表名、动态条件必须可控
- 默认禁止把外部原始字符串直接拼进 SQL

### 10.3 命名与结构

- 使用项目已有的 `DAO` / `Mapper` / `Repository` 命名
- 不要为了统一风格修改现有 namespace、文件名、接口名

---

## 11. 事务与一致性规范

- 涉及多表更新、状态变更、写后回查、异步通知时，评估事务边界。
- 若项目已有统一事务写法，新增同类逻辑保持一致。
- 不把外部慢调用无脑包进数据库事务。
- 涉及重试、幂等、MQ、回调时，明确补偿或防重策略。

---

## 12. 项目专属规则

> 本节最重要。必须填写本项目特有约束，而不是保留空白。

- 新增游戏逻辑落在 `game.js` 的 3. 游戏层；物理与碰撞解算保持为纯函数（入参出参纯数据、不触碰 DOM），便于补测试
- 所有可调数值（重力、速度、跳跃高度、摩擦）放进 `PHYSICS_ENV`，不写魔法数字
- 绘制坐标一律用逻辑坐标系 960×540，禁止直接用屏幕像素坐标
- 物理更新必须走固定步长 `STEP = 1/60`，不得改成与渲染帧率绑定的可变步长
- 跳跃等一次性动作使用边沿触发位（`jumpQueued`），不要用按住持续触发
- DOM id（`stage`/`game`/`hud`/`fps`/`hint`/`pad`）属于对外契约，重命名需同步修改 `index.html` 与 `game.js`
- `TODO` 只用于已知待接入点（敌人 AI、道具、计分、关卡推进），不得用来掩盖未完成逻辑

## 13. 测试与验证要求

### 13.1 AI 改动后的最低验证要求

- 检查函数签名、调用方与纯函数入参顺序是否一致
- 检查调用链是否闭环（输入层 -> update -> 物理 -> 渲染）
- 检查 `PHYSICS_ENV` 参数与 `WORLD`/地面高度是否自洽
- 检查 `index.html` 的 DOM id 与 `game.js` 中的查询是否一一对应

### 13.2 高风险改动重点自查

- 物理参数调整（重力/速度/摩擦/跳跃高度）
- 边界与地面碰撞解算（`resolveCollisions`）
- 输入映射与边沿触发（`KEY_MAP`、`jumpQueued`）
- 状态流转与关卡推进
- 计分与结算
- 缩放与自适应（`resize`、DPR）

### 13.3 无法自动测试时

至少说明：

- 改动影响范围
- 关键调用链
- 建议人工验证的场景

## 14. 禁止事项清单

- 禁止把通用模板硬套到项目现有返回结构
- 禁止仅凭通用框架经验替换项目既有实现方式
- 禁止一次需求扩展成全仓重构
- 禁止无上下文地新增抽象层
- 禁止吞异常
- 禁止输出无业务标识的空泛日志

---

## 15. 给 AI 的执行清单

1. 先定位功能属于哪个模块和哪一层。
2. 搜索同类实现，优先复用周边模式。
3. 确认返回结构、异常体系、日志风格、数据访问命名是否与周边一致。
4. 仅修改与需求直接相关的调用链代码。
5. 检查接口、服务、数据访问、配置、测试是否闭环。
6. 检查异常分支、日志、状态码、动态 SQL 或查询安全性。
7. 输出结果时说明影响范围与验证建议。

这份规范的核心不是“写出最理想的新代码”，而是“在具体项目里写出最不容易出事故、最容易被团队接手的代码”。
